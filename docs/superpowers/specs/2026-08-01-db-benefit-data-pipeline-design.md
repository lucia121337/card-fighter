# 혜택 데이터 원본화 & 전수 검수 파이프라인 설계

- 작성일: 2026-08-01
- 브랜치: feature/benefit-calculator
- 관련 코드: `benefit-calc.js`, `benefits_structured.json`, `card_detail/*.json`, `qa.html`, `benefit_calculator_wide.sqlite`

---

## 1. 배경 & 문제

혜택 계산기의 정확도를 높이는 과정에서 데이터 신뢰도 문제가 드러났다.

- **benefits_structured.json** (계산기 런타임 데이터, 1,563장, LLM 추출):
  요율(할인율·적립률·정액원)·마일·포인트 등 rich 필드는 잘 파싱돼 있으나,
  **전월실적 구간별 한도(tiered cap)가 최상단 1개로 붕괴**(구간 정보 손실).
- **benefit_calculator_wide.sqlite** (`혜택계산기` 테이블, 9,153행 = 카드×카테고리, 사용자 제작):
  **구간별 통합한도(구간1~10)는 보유**하나 **요율 컬럼이 없고**, 그 구간 한도의 **약 50%가 파싱 오염**
  (인접 숫자 병합 아티팩트: 예 `1015000` = "10"+"15000", 연도 유출 `2023`, `cap≤0`, 비단조, 없는 한도 날조).

즉 **DB도 JSON도 불완전한 기계 파싱 근사치**다. 정답은 원문(`card_detail`)이며, 신뢰 가능한 확정 경로는 **사람의 원문 대조 전수 검수**뿐이다.

## 2. 목표 / 비목표

**목표**
- 계산에 필요한 데이터를 **사람이 표(DB)에서 나눠 검수**할 수 있는 원본으로 정리.
- DB를 source of truth로 삼고, **`DB → build → benefits_structured.json`** 파이프라인 구축.
- DB의 오염된 구간 한도를 **제거**하고, 원문에서 **정확히 재적재**.
- 1,563장 **전수 검수**를 팀이 충돌 없이 분담하는 작업규칙 확립.

**비목표 (YAGNI)**
- DB를 브라우저가 직접 읽게 만들기 (정적 사이트는 JSON을 fetch — DB는 authoring 전용).
- rich 필드(택1·마일·포인트·바우처·서비스)를 DB에서 원문 재추출로 새로 뽑기 → 기존 LLM 추출을 병합해 재사용.
- 계산기 로직(benefit-calc.js) 대규모 변경 — 스키마는 현행 유지, 데이터만 정확해짐.

## 3. 결정된 방향 — 설계 B (하이브리드 빌드)

> 사용자 확정: "DB를 원본으로", "설계 B", "사람 검수 나눠서".

- **DB가 원본**으로 보유·검수하는 필드(표로 검수하기 좋은 것):
  요율, 구간별 한도(tier), 연회비, `min_prev_spend`(전월실적 문턱), 카테고리, 상세내용(원문 근거).
- **rich 필드**(표로 나쁘고 이미 LLM이 잘 뽑은 것 — 택1·마일·airline·포인트 프로그램·바우처·서비스·무이자)는
  **build 시 기존 benefits_structured.json에서 병합**.
- 요율은 기존 JSON에서 적재(코드, 무비용), 구간은 원문 재파싱(코드, 무비용) + 오염 제거, **잔여 애매분만 LLM**(바운드된 소액).

**설계 A(완전 재모델·전량 LLM 재추출)를 채택하지 않은 이유**: LLM 대량 재추출 비용이 크고, rich 필드는 이미 품질이 좋아 재작업 실익이 낮음.

## 4. 아키텍처 / 파이프라인

```
                          기존 LLM rich 필드(benefits_structured.json)
                                          │ (병합)
card_detail/*.json ──[재파싱: 구간·요율]──► DB(혜택계산기, 확장) ──[build_from_db.py]──► benefits_structured.json ──► 계산기
   (원문 = 진실)                              ▲
                                              │ 검수·교정
                                     사람 전수 검수 (샤드 분담)
```

- **원문**은 불변(진실의 기준). DB/JSON은 파생.
- DB는 **authoring/검수 원본**. 런타임은 build 산출물 JSON.
- 파이프라인은 **재실행 가능(idempotent)**. 원문은 그대로라 언제든 재파싱·재빌드 가능.

## 5. DB 스키마 확장

현재 `혜택계산기`(카드×카테고리)에 계산·검수용 컬럼을 추가한다. (기존 컬럼 유지, ADD COLUMN)

| 추가 컬럼 | 뜻 | 출처 |
|---|---|---|
| `요율` (REAL) | 할인율/적립률(0~1). 정액·리터당은 아래 별도 | 기존 JSON 적재 → 사람 검수 |
| `요율종류` (TEXT) | `percent` / `fixed_won` / `won_per_liter` / `mile_per_won` / `point_per_won` | 파생 |
| `정액원` (INT) | 정액 할인 원 (fixed_discounts.won) | JSON |
| `리터당원` (INT) | 주유 리터당 원 | JSON |
| `카테고리_전월실적` (INT) | 이 카테고리 혜택의 min_prev_spend | 원문/JSON |
| `구간출처` (TEXT) | `db-reparse` / `db-est`(오염 잔존) / `human` / `null` | 파이프라인 |
| `검수상태` (TEXT) | `unreviewed` / `reviewing` / `done` | 사람 |
| `검수자` (TEXT), `검수일` (TEXT) | 담당·시점 | 사람 |
| `검수메모` (TEXT) | 원문 대조 시 근거·이슈 | 사람 |

- 구간1~10 한도는 **오염분을 null로 비운 뒤** 재파싱 값으로 채운다(§6).
- 단위 혼용 금지 원칙 유지: `요율`(%)·`정액원`·`리터당원`·`mile/point`는 서로 다른 컬럼으로 분리.

## 6. 데이터 적재 계획 ("제대로 적재")

세 단계, 대부분 코드(무비용):

**6-1. 오염 제거 (무비용)** — `scripts/db_clean_tiers.py`
- 위생 게이트 실패 구간을 null로: `cap≤0`, `cap>300,000`, 임계값 범위 이상(`>3,000,000`/`<0`), 비단조.
- 결과: 깨진 값이 build로 흘러가지 않음. 지운 카드·사유를 로그로 남김.

**6-2. 요율 적재 (무비용)** — `scripts/db_load_rates.py`
- benefits_structured.json → DB 매핑: (card_idx, 혜택카테고리) 기준.
  - JSON `category_rates[cat]` → `요율`(percent)
  - JSON `base_rate` → 카테고리 `모든가맹점`/`무실적` 행
  - JSON `fixed_discounts[]` (category 매칭) → `정액원` + `카테고리_전월실적`
  - JSON `fuel_discounts[]` → `주유` 행 `리터당원` + min_prev
  - JSON miles/points → `항공마일리지`/포인트 행
- 24종 DB 카테고리 ↔ JSON 구조 **매핑 표**를 스크립트 상단에 명시(리뷰 가능).

**6-3. 구간 재파싱 (무비용) + 잔여 LLM(선택·바운드)** — `scripts/db_reparse_tiers.py`
- 원문 `key_benefit[].info`에서 **정형 패턴** 추출:
  "전월 … N만원 이상 … X원" / "통합 월 할인 한도 …" 다단 표.
- 재파싱 성공분 → `구간출처='db-reparse'`. 실패/애매분 → `db-est`(오염 잔존 표시) 또는 비움.
- 코드로 못 건진 소수만 LLM 재추출 대상으로 목록화(별도 승인 후 실행).

**검증 지표**: 재파싱 전/후 clean 통과율, JSON category_rates와 DB 요율 불일치 건수 리포트.

## 7. build_from_db.py — DB → benefits_structured.json

- DB의 (card_idx별) 행을 모아 **계산기 스키마**로 조립:
  - `category_rates`/`category_caps` ← DB 요율·구간(대표 통합한도 or 카테고리 한도)
  - `cap_tiers` ← DB 구간1~10 (재파싱 clean만; `db-est`는 제외 또는 플래그)
  - `fixed_discounts`/`fuel_discounts`/`base_rate`/`pre_month_money` ← DB
  - `pick_one`/miles/points/voucher/service_benefits/installment ← **기존 JSON 병합**(rich)
  - `annual_fee`/`type` ← DB
- **단위 분리·최대기준 원칙** 유지. `_src` 계보 표기: `db+llm`.
- **출력 전 검증**: 스키마 필수 키 존재, 숫자 유한, 카드수 일치(±기존).

## 8. 사람 전수 검수 워크플로 & 작업규칙

브라우저는 SQLite를 직접 못 읽으므로, **DB를 샤드 JSON으로 export → 검수 → import back** 한다.
(사용자 기결정: "샤드 파일로 분리")

**8-1. 분담 축 — 카드사 기준 균등 배분 (권장)**
- 총 1,563장 / 54개사. 상위 8개사(KB216·신한206·우리169·현대145·롯데137·NH131·하나123·삼성112)=79%.
- 인원 N에 맞춰 **카드 장수 ~균등**하게 카드사를 묶어 배분(대형사는 1인 1사, 롱테일 46개사는 묶음).
  - 예(6인): ①KB ②신한 ③우리+제주+전북 ④현대+씨티 ⑤롯데+NH일부 … 각 ~260장.
- 대안: idx 균등 구간 — 단순하나 한 사람이 여러 카드사 혼재.

**8-2. 샤드 파일 & 충돌 방지**
- `data/review_shards/<담당>.json` — 각자 자기 파일만 수정 → **충돌 0**.
- 각 샤드 행: card_idx·카드명·카테고리·(DB 현재값)·(원문 발췌)·검수상태·검수메모.
- 병합 시 `build`가 샤드 → DB import → JSON 재생성. (CONTRIBUTING §6 "파일 단위 담당"의 데이터판)

**8-3. 검수 뷰어**
- `qa.html` 확장 또는 `review.html` 신설: 왼쪽 DB 현재값(요율·구간)·오른쪽 원문 나란히,
  행별 **[교정]·[검수완료]** 입력. (읽기 전용 qa.html에 편집·플래그·진행률 추가)
- 진행률·의심 자동 플래그(§ qa 기존 규칙) 재사용.

**8-4. 검수 절차 (1장 기준)**
1. 원문(상세페이지 ↗)과 DB 요율·구간 대조
2. 틀리면 교정 + `검수메모`에 근거, 맞으면 `검수상태=done`
3. 애매/원문불명은 `reviewing` + 메모 → 팀 논의
4. 담당 샤드 완료 → PR (CONTRIBUTING §2 흐름) → build 재생성 → 계산기 확인

**8-5. 규칙(요약)**
- main 직접 금지, feature 브랜치 + PR(기존 규칙 준용).
- **자기 샤드 밖 수정 금지**(남의 카드사 건드리기 전 공유).
- 커밋 메시지 `data: <카드사> 검수 N장` 형식.
- **DB 원본/스크립트(공통 파일) 수정 시 팀 공유**(CONTRIBUTING §6-3 준용).
- 원문과 다르면 **원문 우선**. 추정으로 채우지 말 것(비우고 메모).

## 9. 검증 & 롤백

- 각 스크립트는 **dry-run 우선**(변경 건수·예시 출력) 후 적용.
- build 후 **계산 회귀 테스트**: 대표 프로필(헤비/소액) 순위·과대/과소계상 무회귀. 기존 `test_fixed_gating.js` 패턴 확장.
- 생성 JSON vs 현행 JSON **diff 리포트**(카드별 money 변화 top-N).
- 원문 불변 → 문제 시 언제든 재파싱·재빌드로 롤백.

## 10. 비용

- 6-1 오염제거 / 6-2 요율적재 / 6-3 정형 재파싱 / 7 build: **코드, 토큰 ≈ 0**.
- 잔여 LLM 재추출: **선택·바운드**(코드로 못 건진 소수만, 별도 승인).
- 사람 검수: 팀 분담(1,563장 / N인).

## 11. 리스크 & 미결정

- **DB 카테고리(24) ↔ JSON 구조 매핑**의 정확도 — 매핑 표를 사람이 1차 리뷰 필요.
- **정형 재파싱 커버리지 미지수** — 실제 돌려봐야 몇 %인지 나옴(6-3 지표로 측정).
- **rich 필드 병합 계보** — `_src` 표기로 추적, 검수 중 rich 필드도 틀리면 별도 처리.
- 검수 인원 수 N — 미정(8-1 배분은 N 확정 후 표 확정).
- 두 데이터(DB·JSON) **일시 공존 기간**의 동기화 — build를 단일 관문으로.

## 12. 실행 순서 (마일스톤)

3. **M3 구간 재파싱**: `db_reparse_tiers.py`, 커버리지 측정, 잔여 목록화.

5. **M5 검수 인프라**: 샤드 export + `review.html` + 분담표 확정.
